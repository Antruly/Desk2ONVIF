# Desk2ONVIF 工程实录

> 这是项目的**开发实录**，不是上手文档 —— 想看「这是什么、怎么装、怎么跑」
> 请回 [`../README.md`](../README.md)。
>
> 本文保留了大量**踩坑记录**和**变异检验**的过程（「陷阱 89」「三条断链」之类），
> 因为这里几乎每一个真被翻出来的缺陷，都是脚本和别人对账的时候暴露的，而不是
> 靠读代码看出来的。留着它们是为了下次改到同一处时能先看到「上次为什么坏」。
>
> 文中出现的相对路径（`scripts\`、`packaging\`、`third_party\` 等）都是
> **相对仓库根目录**的，不是相对本文件。

把 Windows 桌面伪装成一台 **ONVIF Profile S** 网络摄像机：海康、大华等 NVR
能像发现普通 IP 摄像机一样自动发现它（WS-Discovery），把它作为 IP 通道加入，
然后拉取 H.264 视频流。

```
DXGI 桌面复制 ──► 指针合成 ──► FFmpeg / libx264 ──┬──► Live555 RTSP ──► NVR / VLC / ffplay
   (采集线程)                                  │    (调度线程)   ├─ /live      主码流
                                               │                 └─ /live_sub  子码流
                                               ├──► fMP4 over WebSocket ──► 浏览器预览
                                               └──► MJPEG ──► GET /snapshot.jpg

libuvcpp（HTTP / WebSocket / ONVIF SOAP / WS-Discovery UDP 3702）
```

主、子两路是**两个独立的 x264 实例**，同一张 BGRA 进去、各自缩放到自己的目标尺寸
（不是"编一次再抽帧"，也不是"编一次再解码"）。子码流见下面「两路码流」。

第五轮起上面**整条管线按通道各一份**：一块屏一路（默认自动发现、默认开），本机
摄像头也能加进来当一路。多出来的是"有几路"，每一路内部仍然是这张图 —— 见下面
「多通道」。

一条命令起一整台"摄像机"：

```powershell
# 桌面 → RTSP + ONVIF + Web UI。**ONVIF 默认就是开的**，不用加开关
.\build\bin\desk2onvif.exe --rtsp --http

# 看看这台机器有哪些输出，哪些真的能录
.\build\bin\desk2onvif.exe --list-displays

# 看看这台机器有哪些摄像头（Media Foundation）
.\build\bin\desk2onvif.exe --list-cameras

# 摄像头当通道 1（那块屏就自动成为通道 2）
.\build\bin\desk2onvif.exe --camera "FHD Camera" --rtsp --http

# 录 10 秒
.\build\bin\desk2onvif.exe --record out.mp4 --seconds 10

# 推 RTSP（默认 rtsp://<本机IP>:554/live），拉流看
.\build\bin\desk2onvif.exe --rtsp --seconds 60
ffplay -rtsp_transport tcp rtsp://127.0.0.1:554/live

# 依赖自检
.\build\bin\desk2onvif.exe --selfcheck
```

Web / ONVIF 起来之后：

| 入口 | 说明 |
|---|---|
| `http://<本机IP>:8080/` | Vue 控制台，**没登录会先跳到登录页**。路由：`/` 预览（首页）、`/status` 状态、`/config` 配置、`/login` 登录 |
| `POST /api/login` | `{"user":…,"password":…}` 换一个会话 cookie。同一个 IP 在 5 分钟内错满 5 次会锁 60 秒（429 + `Retry-After`，冷却期内**正确口令也拒**） |
| `GET /api/session` | "我登录了吗"。**匿名可达** —— 前端进任何页面前都先问这一句 |
| `POST /api/logout` | 让浏览器丢掉 cookie（服务端无状态，见下） |
| `GET /api/status` | fps、码率、队列、观众数、ONVIF 与预览的计数；**逐路一份**（`rtsp_streams` 数组 + 多通道的 `channels` 数组，后者带每路的 ONVIF 端口、RTSP 路径、状态、录像字节数） |
| `GET|POST /api/config` | 读写配置（返回的是**实际生效值**，含命令行覆盖） |
| `GET /api/sources` | 本机的画面源清单：每块显示输出（名字、分辨率、位置、**能不能抓**）+ 每个摄像头（友好名）。配置页「检测到的源」用的就是它 |
| `GET|POST /api/preview-channel` | 网页预览"现在看第几路"。**这个状态是全机一份、活在进程里**（不是每个标签页一份），所以刷新页面、换个浏览器看到的还是同一路 —— `/api/snapshot.jpg` 也跟着它走 |
| `POST /api/onvif/restart` | 重新组播 Hello（NVR 那边"搜不到"时用） |
| `GET /api/snapshot.jpg` | **当前预览通道**的画面（MJPEG，`Cache-Control: no-store`）。**要会话 cookie**，且**永远不发** Digest 挑战 |
| `GET /snapshot.jpg` | 同一个画面，**给 NVR 用的**（`onvif.snapshot_path`）。认两种凭据：会话 cookie 或 ONVIF Digest；ONVIF 开着时**必定**先发挑战 |
| `WS /ws/stats` | 每秒推一次状态 JSON。未登录会被后端用 **1008** 关掉（不是 401 —— WS 升级不经过 HTTP 的鉴权中间件） |
| `WS /ws/preview` | fMP4 分片，浏览器 MSE 直接播（延迟约 1 个 GOP）。同样受 1008 守卫。**一次只推一路**（见「多通道 → 预览页为什么一次只看一路」） |

`POST /onvif/device_service` 是设备服务，`POST /onvif/media_service` 是媒体服务。
除了 `GetSystemDateAndTime`（规范要求匿名），其余操作都要 **HTTP Digest**；
用户名/口令默认都是 `admin`，配置项是 `onvif.user` / `onvif.password`。

> **Web 控制台默认要登录，而默认口令 `admin` 就印在 `--help` 里** —— 加上默认
> 监听 `0.0.0.0`，等于**出厂状态下同一局域网内任何机器都能用 `admin`/`admin`
> 进来**看你的桌面画面、读配置、改配置。所以：
>
> - **只给本机用**：加 `--http-host 127.0.0.1`。最省事，也最安全。
> - **要给 NVR 或别的机器用**：务必换掉口令 —— `--http-password <口令>`，
>   或配置文件的 `web.password`；用户名同理（`web.user`）。
>
> 四点容易踩的：
>
> - **Web 的凭据和 ONVIF 的是两套**（`web.user`/`web.password` 对
>   `onvif.user`/`onvif.password`）。改 ONVIF 那个口令**不会**保护这个控制台。
> - **关掉登录**（`--no-http-auth`，或 `web.auth_enabled=false`）等于把"读配置、
>   改配置、看桌面画面"三件事一起交出去，启动时会打一条 WARN。
> - 口令设成**空串**不是"关掉鉴权"，而是"口令就是空"：登录框照常出现、校验
>   照走，任何人按一下回车就进去了。留空时会打 WARN，而不是安静地开门。
> - 会话的签名密钥是**每进程一份的随机数**，不是口令本身。所以**重启程序会把
>   所有已登录的人踢下线**（通常正是想要的）；反过来，**改口令不会踢人** ——
>   已经发出去的 cookie 一直有效到 7 天后过期。要立刻清空所有人只能重启。

> **从安装包装出来的，第一次打开网页请用安装时填的那个账号口令** ——
> 不是 `admin`/`admin`。向导里那一对会被同时写进 `web.user`/`web.password`
> 和 `onvif.user`/`onvif.password`（细节与踩过的坑见「安装时的口令」）。
> 绿色版解压出来没有这一步，那一份是内置默认值。

`--list-displays` 会对每个输出**真的**建一次桌面复制会话再关掉。这是判断
"能不能录"的唯一可靠办法 —— 按适配器名字去猜（"名字里有 idd/virtual 就当
虚拟屏"）只能覆盖已知的几个厂商，还会误伤真实硬件。

`--record` 的完整选项见 `--help`。不给 `--seconds` 就一直录，Ctrl+C 停止
（会正常收尾把 MP4 索引写完，不是硬杀）。

**录制中途换了分辨率会分成多个文件。** `--record out.mp4` 在显示器分辨率变了
之后是 `out.mp4` + `out.1.mp4` + `out.2.mp4`……而不是一个文件：

```
$ desk2onvif --record out.mp4 --seconds 40
[WARN ] 采集尺寸从 2880x1920 变成 2560x1600：编码器、MP4 轨道和 SDP 里都写死了
        旧尺寸，就地换不了。这一段落盘收尾，下一段按新尺寸重开。
这一段录到 out.mp4 —— 30.1s，900 包（30.0 fps），...
接着录：换分辨率之后编码器/封装/SDP 都得按新尺寸重建，所以从这里另起一段（out.1.mp4）。
...
  分段    : 共 2 段（中途换了 1 次分辨率）
```

**为什么不能是一个文件**：H.264 的 SPS/PPS、MP4 的轨道头（`avcC` 里的尺寸）、
SDP 里的 `sprop-parameter-sets` 全都在创建时就把宽高写死了，中途改只会得到一个
解不出来的文件。所以新尺寸是**新的一段**：新的编码器、新的 MP4、RTSP 服务在
同一个端口上重开。每一段都是独立可播的完整文件，`--seconds` 是**整段运行**的
预算（两段加起来 40 秒，不是每段 40 秒）。

不想分段就固定显示模式，或者先关掉会自动切分辨率的程序。一段里连续换超过 8 次
会停下来报错 —— 那种情况说明有东西在反复改模式，再录下去也只是反复重建。

> **接 NVR 之前先看防火墙。** Windows 对入站连接默认全拦，而本机 `ffplay` 拉流
> 走回环、**不受防火墙影响** —— 所以"NVR 搜不到设备 / 添加时超时"的第一嫌疑人
> 就是它。先查：
>
> ```powershell
> .\build\bin\desk2onvif.exe --firewall status --rtsp --http     # 只读，不需要管理员
> .\build\bin\desk2onvif.exe --firewall print  --rtsp --http     # 只打命令，自己抄去执行
> .\build\bin\desk2onvif.exe --firewall add    --rtsp --http     # 直接加（要管理员）
> ```
>
> 加出来的规则只对**同网段**、**专用/域网络**放行（`profile=private,domain
> remoteip=localsubnet`）—— 不是"对全世界开放"。NVR 在别的子网/VLAN 里的话，
> 用 `print` 把命令打出来，把 `remoteip=localsubnet` 改掉。
>
> 它**只在你显式调用时才碰防火墙**：`--rtsp`/`--http` 起服务时一行规则都不会改。
> 一个录屏工具不声不响地把端口对局域网开放，是使用者从没同意过的事。

> **录制期间显示器断了/换了分辨率会怎样**：捕获会话失效（`DXGI_ERROR_ACCESS_LOST`）
> 会被自动重建，而且是**不放弃**的重试（退让 150 ms → 2 s，显示器接回来就自动接上）。
> **尺寸没变**就接着录同一个文件；**尺寸变了**则这一段落盘收尾、按新尺寸另起一段
> （见下面"分段"那节）—— 编码器的 SPS/PPS、MP4 轨道头、SDP 里都写死了旧尺寸，就地
> 换只会得到一个解不出来的文件。三种触发路径都实测过，见下。

## 配置热生效：能改的当场生效，改不了的逐字段告诉你

`POST /api/config` 的回应里**没有**一个笼统的 `restart_required` 布尔值，而是
两个数组 `applied` 和 `pending`：

```json
{ "applied": ["onvif.model"], "pending": ["rtsp.sub_height"], "restart_required": true }
```

一次保存里"这项当场生效、那项要重启"是常态，只给一个布尔值时前端只能二选一，
而**两种选法各有一半的时候在骗人**。逐字段报是把这件事说清楚的最小粒度。

当场生效的有两组：

- **ONVIF 的身份与凭据**（`manufacturer` / `model` / `firmware_version` /
  `hardware_id` / `serial_number` / `device_name` / `location` / `user` /
  `password`）—— 它们每次响应现读，改完下一次 `GetDeviceInformation` /
  Digest 挑战就是新值，**不用重启、不用重连**。
- **Web 控制台的登录开关与凭据**（`web.auth_enabled` / `web.user` /
  `web.password`）—— 改完下一次登录就用新的。有一点要知道：**它不会把已经
  登录的人踢下线**（令牌签的是每进程一份的随机密钥，不是口令），所以"改了口令
  怎么还进得去"不是 bug —— 要立刻清空所有登录，只能重启程序。

其余全部要重启：采集参数要重建编码器，端口要重新 bind，都做不到热改。

**热/冷的边界不是一张手写的清单**，而是"这次保存实际同步进了哪些字段"倒推
出来的：`diff_config(cfg, next)` 得到"变了什么"，`diff_config(cfg, running_cfg)`
得到"还没生效的"，两者相减就是 `applied`。手写清单迟早会和真正同步的那几行
代码不一致，而症状恰好是它要防的那一种 —— 某个字段改了却没进 `pending`，
界面上显示"已生效"。

`GET /api/config` 上也带 `pending`。只放在 POST 回应里的话，用户存完刷新一下
提示就没了，而表单里显示的又都是新值，看起来一切已生效。

> **码率是改不了的，这一点是证明过的，不是没做。** 实测（`tests/x264_reconfig_check.cpp`）
> 运行中改 `avctx->bit_rate` 后 libx264 封装层不认；`x264_encoder_reconfig` 在
> `avcodec-63.dll` 的**导出表里出现 0 次**，所以 FFmpeg 也没有别的路可以把它
> 递下去。顺带一提，这个问题不是"懒得做"，是**在这条链路上无解**。

## 网页控制台：左边一栏，按「能不能改」分组

外壳是「左侧栏 + 工作区」：侧栏可以折叠（按钮在左上角，状态记在
`localStorage`），默认展开；窗口窄到 720 px 以下时它变成覆盖式抽屉，由顶栏的
汉堡按钮开合。收起时只剩图标，每个图标带 `title`。

菜单按**用户点名的三分法**分组 —— 分组本身就是回答"这一页是干什么的"：

| 组 | 项 | 路由 |
|---|---|---|
| 监控 | 预览（**首页**） | `/` |
| 监控 | 实时状态 | `/status` |
| 配置 | 图像设置 | `/config#video` |
| 配置 | 水印 OSD | `/config#osd` |
| 配置 | 音视频 | `/config#audio` |
| 配置 | 时间设置 | `/config#time` |
| 配置 | ONVIF 设置 | `/config#onvif` |
| 配置 | 系统设置 | `/config#system` |
| 设备 | 设备信息（**只读**） | `/info` |
| 设备 | 操作日志（**只读**） | `/logs` |

「配置」那六项**指向同一页的不同段落**，不是六个页面 —— 表单和保存按钮只有
一份，点菜单只是滚过去。代价是保存条必须**粘在视口底部**（`position: sticky`），
否则从「系统设置」往下看就会发现找不到保存按钮，那等于用锚点制造了一个新的
「找不到保存」。

> ⚠️ 实现上有两处容易漏，症状都是「点了菜单没反应」：锚点跳转要在**配置异步
> 加载完之后再滚一次**（首次滚动发生在页面还很短的时候），以及在**已经停在
> `/config` 时再点另一个菜单项**要单独盯 `route.hash` —— 那时组件不会重挂，
> 路由的 `scrollBehavior` 根本不会被调用。

> ⚠️ **验这件事的那把尺子自己也错过一次：「固定睡 400 ms 再判落点」，在平滑滚动
> 还没滚完时，把「还在滚」报成了「压根没滚」—— 而两者报出来是同一个 `false`。**
> 这一页有**两条**滚动链（router 的 `scrollBehavior` 与 `ConfigView` 里那个 watch），
> 两条都是 `behavior: 'smooth'`，**「滚完了」这件事没有一个可断言的时刻**，
> 只有一个可观测的终点。量出来的：把采样预算缩到 8 次（≈400 ms）当旧尺子跑，
> `config_probe.mjs` 报 **通过 51 项 / 失败 1 项** ——
>
> ```
> [FAIL] 点菜单「音视频」之后那一段滚进了视口（top=874 视口高=720 scrollY=3064，407ms / 8 次采样后位置不再变）
> ```
>
> 而同一次留下的滚动轨迹是 `0:9 51:67 101:213 152:529 203:1166 253:1911 304:2425 357:2822`
> —— 八次采样**每一次 `scrollY` 都在涨**，到预算用完时还在爬。也就是说 `top=874`
> 不是「滚错了地方」，是「截了一张半路上的图」。改成**轮询到位置稳定为止**（50 ms 一步、
> 连续两次相同才停、60 次上限）之后同一个页面 **52/0**。多出来的那一项是同时补上的
> 鉴别器：先单独断 `location.hash === '#audio'` —— 少了它，「菜单项写错了锚点」
> （URL 变了、页面纹丝不动）和「锚点对了、只是滚动没生效」在报告上是**同一个 `false`**，
> 而这两件事一个要改菜单、一个要改滚动。
>
> **判据：任何「点一下 → 等一会儿 → 断言结果」的断言，先问「等」是在等一个事件，
> 还是在赌一个时长。** 平滑动画、异步加载、网络往返都属于**没有完成时刻、
> 只有完成状态**的那一类，它们的正解是**轮询到状态稳定**（并把中途每一次取样一起报出去
> —— 一条从 0 爬到目标值的轨迹和从头到尾一个数，一眼就能分开）；而「滚没滚」这种复合问题
> 要**先拆成两条各自可断的断言**，否则两种完全不同的故障共用一个失败信号。

预览页（首页）的**快照是点了才抓的**：进页面只起 MSE 实时预览，`<img>` 只在
按下「抓拍」之后才出现。抓的是 `/api/snapshot.jpg`（带一个 nonce 参数）而不是
`/snapshot.jpg` —— 后者会给浏览器发一个 Digest 挑战，弹的是**系统原生的**口令
框，而不是页面里的。设备信息页把「加进 NVR 时填这些」摆在一起（地址 + 用户名），
地址类字段都带复制按钮。

## 水印（OSD）：网页和 NVR 两条路，改完画面下一帧就变

水印现在是**热生效**的：网页上改，或者 NVR 调 `SetOSD` / `CreateOSD` /
`DeleteOSD`，**画面下一帧就换**，不重建管线、不分段。

这件事以前是反过来的 —— 「要重建整条管线才变」是当初**刻意**的设计（让每一段
录像里的水印自洽）。改成热生效之后，代码里那段说"故意不生效"的注释**一并改掉
了**：留着它就变成误导。副作用是好的：`osd.*` 全部从 `pending` 进 `applied`，
于是**界面上说「已生效」和画面上真的变了是同一件事**。

- 「**移除**」和「**关闭**」是两件不同的事，界面上分得开：关掉是留着一项、随时
  能再开；删掉就是没有了。最多 4 项。
- 位置可以四角选，也可以**在预览底图上拖着放** —— 拖完变成 `custom` +
  `x_pct/y_pct`。底图**按需抓**（一个「取当前画面」按钮），不自动抓。
- 字号 `0` = 自动（帧高 / 32）。拖动和换字号都自然生效，因为字形掩码的缓存键是
  （文字, 字号），**位置不在缓存里**。

> ⚠️ **NVR 那条路有防抖。** NVR 会**周期性重复下发同一份 OSD**，不拦的话每次
> 都要白写一遍盘、日志还会被淹没。判据是「改动前后的 OSD 序列化字符串是否
> 相同」，只有真变了才写盘 + 置生效 + 打一行 INFO。这一条与审计那边 60 秒的
> 去重闸门是两件不同的事，别混为一谈。
>
> ⚠️ **水印热生效意味着一整段录像里可能有两种水印位置。** 「要重启才变」不是
> 懒，是刻意让每段自洽；按用户要求改成即时之后，这个取舍写在这里，而不是留给
> 人自己发现。

NVR 侧（海康那一类）**本来就能设水印和名称** —— 这一轮只是让它的改动立刻反映到
画面上，协议层一行新代码都没写。那一整套（`GetOSDs` / `SetOSD` 改位置 /
`CreateOSD` / `DeleteOSD`）在 `tests/onvif_soap.py` 的 `[11a]`–`[11j]` 里，改完
位置**不重启**即从 `/api/status` 和一次快照上断言画面已变。

## 时间：设备时间、NTP、以及 NVR 来对时

**先说清楚它动的是什么。** 本机有一个「设备时间」= **主机时间 + 偏移**，画面
水印上那个时间和 ONVIF 报出去的那个时间用的都是它。**它绝不改 Windows 的系统
时钟** —— 不需要管理员权限，也不连累这台机器上别的程序。代价要说全：

> ⚠️ **文件的时间戳、日志的时间戳是主机时间；画面水印和 ONVIF 报出的是设备
> 时间。** 两者可以差出几分钟甚至几小时（NVR 对时或手动校准之后）。取证场景
> 通常正是要它对齐录像机，但这个差异是存在的，得知道。
>
> ⚠️ **偏移是整秒**（`DeviceState::offset_s_` 是 `int64` 秒），NTP 的亚秒部分会
> 被丢掉。水印是秒级显示，没有影响 —— 但**别把它当精密对时用**。

三条路都在网页上（侧边栏「配置 → 时间设置」）：

| 做什么 | 接口 / 落点 |
|---|---|
| 手动校准 | `POST /api/time`，body 可以给 `{"offset_s": n}`，也可以给一个绝对时刻由服务端算偏移；写进 `time.offset_s` + 存盘 + 进审计 |
| 立刻对时 | `POST /api/time/sync` —— **回 202**，真活在后台线程做（UDP 查询是阻塞的，不能占住 web 循环，它同时还管 WS 推送和 SOAP） |
| 归零 | `POST /api/time/reset` = 回到主机时间 |

- **偏移落进配置是刻意的**：手动校准出来的偏移重启后要还在（NTP 那条路可以
  自己再对，手动那条不行）。恢复出厂删掉 `config.json` 时它自然归零。
- **NTP 失败分得清三种**：`timeout`（收不到回包）/ `bad_reply`（回包太短或
  `Stratum == 0`，即 KoD 服务器拒绝）/ `unreachable`（连地址都拿不到）。
  这一条不是洁癖：UDP 到公网 123 在没有网络时会被防火墙**静默丢弃**（UDP 没有
  RST），所以「发出去成功」和「服务器没理我」长得一模一样 —— 不分开报，就等于
  在假装成功。
- **对时范围**：默认服务器是公网域名，没网的环境就是对不上；也可以填内网地址
  （不少 NVR / 路由器自带 NTP 服务）。

**NVR 来对时**（用户点名要的那一条）走 ONVIF 的 `SetSystemDateAndTime`：
`UTCDateTime` 或 `LocalDateTime` + `TimeZone` 都认，算出的偏移立刻写进设备时间
（水印下一帧就跟着走、`GetSystemDateAndTime` 立刻报新值）。**只有 `manual` 模式
才落盘** —— NTP 模式下这个偏移下一个对时周期就会被覆盖，写进去只会让配置里多
一个用户从没设过、也不会被采用的数。`DateTimeType` 现在按 `time.mode` 报
`Manual` / `NTP`：手动模式下报 NTP 是不诚实的。

> 「**谁**改的时间」这个问题产品自己答不了 —— `DeviceState` 只记「什么时候被
> 改的」，记不了「被谁改的」。那正是下面那份操作日志存在的理由之一。

## 延时档位：极致低延迟 / 均衡 / 优先画质

`capture.latency` 三选一（外加 `custom`），**只展开 `threads` 和 `gop_seconds`
两个字段**，与画质档位展开的那四项**不相交** —— 所以「流畅 + 极致低延迟」这种
组合天然合法，不需要任何优先级规则。

| 档 | 界面名 | `threads` | `gop_seconds` |
|---|---|---|---|
| `realtime` | 极致低延迟 | 1 | 1 |
| `balanced` | 均衡（**默认**） | 3 | 2 |
| `quality` | 优先画质 | 6 | 4 |
| `custom` | 自定义（手改过那两个字段） | 不动 | 不动 |

命令行也给了一个：`--latency realtime|balanced|quality|custom`（带值，**不进**
`kFlagNames`）。

**`preset` / `tune` / `profile` 三档一律钉死**（`ultrafast` / `zerolatency` /
不指定 profile）。这不是保守，是因为它们是这条链上唯一「看起来只关乎画质、
实际会改协商结果」的旋钮：`preset=ultrafast` 会关掉 CABAC/8x8dct/weightp，
x264 于是把档位降到 **Constrained Baseline，不管 `--profile` 写的是什么**；
一旦「优先画质」把 preset 放松到 `veryfast`，同一个设备的 H.264 profile 就会
从 Constrained Baseline 变成 Main —— 而变化的那几样（NVR 兼容性、`GetProfiles`
报出去的编码参数、子码流的解码开销）**没有一样在档位表上**。判据是：这一档换来
的画质提升，必须**只看 `threads` 和 `gop_seconds` 这两个数**就解释得了。

**它属于「要重启才生效」那一档**（threads / gop 都是编码器构造参数，与码率
同理），照现有机制进 `pending`，并复用音视频段那个「保存并立即应用」
（`POST /api/config` + `POST /api/reload`）—— 不需要任何新的生效路径。

> ⚠️ 选了档位就会把 `threads` **钉成表里的值**，而 `0`（= 按延迟优先自动选、
> 封顶 6）只留给 `custom`。否则「均衡」就不是一个确定的点，而是「跟着自动值
> 走」，档位表也就没意义了。代价是「我什么都没改，怎么跟以前不一样了」——
> 用默认档加一句说明挡住它。

> ⚠️ **这张表是「无条件回写」的，所以每一个直接写 `threads` / `gop_seconds` 的地方
> 都必须同时把 `capture.latency` 翻成 `custom`，否则那次写入会在同一次
> `validate_config` 里被档位值改回去。** 展开就是 `find_latency_tier()` 命中之后那两句
> `snap("capture.threads", …)` / `snap("capture.gop_seconds", …)` —— 它不知道、也没法知道
> **是谁**写的这两个字段。整棵树里只有两处在翻它：网页上手动改那两个字段（`ConfigView.vue`），
> 以及 **NVR 的 `SetVideoEncoderConfiguration`（`GovLength` → `gop_seconds`）**。
> 漏掉 NVR 那一处的症状是这一族里最难查的：**NVR 改完毫无变化，而 SOAP 照样回成功、
> `onvif_service.cpp` 那边的换算代码一个字节都没错** —— 因为值确实写下去了，
> 只是紧接着被档位表改回来了。这一条是量出来的：把 `src\main.cpp` 里
> `if (latency_field) next.capture.latency = "custom";` 那一行拿掉重编，
> `tests/onvif_soap.py` 从 **283/0 掉到 282/1**，**恰好一条红** ——
> `[FAIL] GovLength 36 帧 ÷ 12 fps = 3 秒（实际 2）`；而同一次运行里它旁边那条
> `[OK] GovLength = 50`（回读自洽）照样绿、`web_contract.py` 190/0、`web_auth.py` 51/0
> 一条没动。还原之后同一把尺子量到 283/0、那一行变回 `（实际 3）`。
> 再往下一层，档位表本身的机制是由「分别拿掉两句 `snap`」的变异钉住的：
> 基线 34/0 各掉到 **26/8**。
>
> **判据：给一张「档位表展开成具体值」的表时，先数一遍有几个地方会写它展开的那几个字段，
> 然后为每一个写一条「我写了它、档位被翻成 custom」的断言。** 一句「记住要翻 custom」
> 的注释不是检查。更一般地：**一个会在下游被无条件改写的字段，它的每一个写入点
> 都是一个必须被单独验的分支** —— 这类缺陷的签名是「接口回成功、值没变、
> 两侧的换算代码都没错」。

### 「极致低延迟」这个名字，不是「极致 0 延时」

「让画面延时降低」在这条链上至少是**五件不同的事**，各自的**地板**还不一样高：

| 环节 | 现状 | 本档能碰吗 |
|---|---|---|
| 编码器帧级并行（`threads`） | 每线程 ≈ 一帧的流水线延迟 | ✅ **主旋钮** |
| 关键帧间隔（`gop_seconds`） | 决定「**多久能看到第一帧**」 | ✅ 第二旋钮 |
| 分片节奏（后端） | 决定「**看到之后有多滞后**」 | ✅ 改成不等关键帧，见下 |
| 浏览器里的 `TARGET_LATENCY` | 前端，可调 | ✅ 跟着档位走，见下 |
| 音频那 ~320 ms 的地板 | 环回环 300 ms + AAC priming 21 ms | ❌ 音频一开就有 |
| NVR 侧的抖动缓冲 | 我们看不见 | ❌ |

所以档位名**刻意不叫「极致 0 延时」** —— 那个名字会被量出来证伪（开音频时
地板就有 ~320 ms，网页预览的真值更是秒级）。界面上把**能碰的那几项换成具体
数字**给人看，**碰不到的那几项也一起写出来**：只写"能到多少"而不写"地板在哪"，
用户照样会拿一个够不到的数来对账。

### 网页预览那一半：先把尺子修好，再动旋钮

`PreviewView.vue` **本来就在做低延迟播放器该做的事** —— `alignToLiveEdge()`
把播放头对到直播边缘、`trimBuffer()`、`MAX_DRIFT` 滞回，一应俱全。真正错的是
**它显示的那个数**：`updateLatency()` 算的是 `buffered.end − currentTime`，稳定
显示 `TARGET_LATENCY`（0.5 s）。而 `buffered.end` 是「我们**已经拿到**的数据的
末尾」，不是「画面的现在」—— mov 封装器要等下一个关键帧才知道上一个分片在哪
结束，所以真实延迟里还有一项**分片滞后**，平均半个 GOP、最坏一个 GOP。
`gop_seconds = 2` 时界面写 `0.5`、真值 1~2 秒。

修法是**换一把尺子**：后端在每次预览连接建立、发初始化段时**多发一帧文本**
`{"type":"t0","t0_wall_ms":…,"server_now_ms":…}`，前端于是按墙钟算

```
真实延迟 = now − (t0_wall_ms + 媒体时间 × 1000)
```

界面上**两个数都显示**（`真实延迟` 与 `缓冲余量`）—— 它们的差恰好就是「分片
节奏」那一项。只显示一个数的话，改完分片节奏你会看到一个数纹丝不动，于是以为
改动没生效。

后端那一半是**让分片不再等关键帧**：`flush()` 里那句
`av_write_frame(fmt_, nullptr)` 在任何位置切一刀，不再跟着 GOP 走。
三档还把 `TARGET_LATENCY` / `MAX_DRIFT` 一起挂上了（`realtime` 0.25/1.0、
`balanced` 0.5/2.5 = 今天的值、`quality` 1.0/4.0），并允许**本机覆盖**
（`localStorage`）—— 这两个数取决于看着这块屏幕的这台机器和这条网络，而不是
设备属性；设备给默认值、决定权留给本机，是这两件事唯一正确的关系。

> ⚠️ **`+frag_custom` 不是这件事的开关** —— 这一条是量出来的，而且第一版
> **推反了**。同一段码流、同样的 flush 节奏，`init()` 的 `fragment_on_flush`
> 取真/假各跑一遍：**47/47 个分片、300/300 个样本，两份输出逐字节相同**
> （`tests/fmp4_check.cpp` 的「切碎不等于切坏」就地 `memcmp`，5,139,234 字节）。
> 也就是说这一版 FFmpeg 里 `av_write_frame(fmt_, nullptr)` 本身就切分片，不是
> 有了 `frag_custom` 才切。开关留着只是为了「哪天换一版变成不带它就只在关键帧
> 处切」那条会**无声**退化的路。`fmp4_muxer.h` 里那段注释记着完整的推理、被
> 推翻的旧说法，以及"别拿开/关这个参数编两个构建相减去量延迟"（差恰好是 0）。

### 实测读数（本机，2026-10-08）

`tests/browser/latency_probe.mjs`：屏幕上放一个**受控的闪烁方块**，页面上用
`drawImage(<video>) + getImageData` **从像素里读出**那次变化出现的时刻，与它
真正发生的墙钟相减 —— 这才是端到端真值，界面自报的那个数不能当判据。

| 档 | 像素量出的真实延迟 | 页面自报 | 首个分片 | 第一幅画面 | 分片间隔均值 | 分片数 |
|---|---|---|---|---|---|---|
| `realtime` | **371.6 ms** | 300.0 | 96 ms | 934 ms | 206 ms | 99 |
| `balanced` | **765.0 ms** | 700.0 | 41 ms | 2556 ms | 222 ms | 92 |
| `quality` | **1365.9 ms** | 1300.0 | 148 ms | 3207 ms | 229 ms | 89 |

断言有三条是硬的：「**尺子是诚实的**」（界面自报与像素量出的值之差 < 150 ms）、
「**两个数不是同一个数**」（`真实延迟` 必须**严格大于** `缓冲余量`）、
与「**档位纵向可比**」（`realtime` < `quality`，**只作纵向比较、不判绝对值** ——
绝对值随机器与网络变，判它会假红）。

**顺带量到一件值得记住的事：首个「分片」的时间在三档之间基本是平的
（41–148 ms），而第一幅「画面」的时间严格跟着 GOP 走（934 / 2556 / 3207 ms）。**
这正是「分片节奏」与「关键帧间隔」是两件事的正面证据：前者管「数据什么时候到」，
后者管「多久能看到第一帧」。

> ⚠️ **「尺子是诚实的」这一条的鉴别力，偷偷挂在一个没人写进前提的条件上：跑的是哪一档。**
> 它判的是「页面自报的真实延迟」与「像素量出来的值」之差 < 150 ms —— 而换回旧公式
> （`buffered.end − currentTime`）时，页面上那个数**恰好就是「缓冲余量」那一项**，
> 两者之差正好等于**分片滞后**。`balanced` 档实测分片滞后只有 **106 ms < 150 ms**，
> 所以**旧公式在这条断言下照样绿**（页面上那个数从 700 掉到 552，差值 137.2 ms，通过）。
> 也就是说它只在「分片滞后 > 容差」的档位上才有鉴别力。
>
> 补的第三条换了一个**与档位无关**的问法：**两个 chip 是不是同一个数**。新公式下
> `真实延迟 = 分片滞后 + 缓冲余量`，所以它**恒大于**「缓冲余量」；旧公式下两者逐位相同
> （`total = d * 1000`、`buffered = d`）。实测差值：新公式 `realtime` **24.0** /
> `balanced` **106.0** / `quality` **210.6** ms，旧公式 **0.0 ms（精确）**。
> 判据只用「严格大于 + 一个几毫秒的 epsilon」，**不设下限** —— 设下限就等于把这个判据
> 重新挂回「这台机器的分片滞后有多大」上，那正是要躲开的东西。
>
> **判据：一条「两个数应当接近」的断言，先问一句它的鉴别力从哪来。** 如果鉴别力来自
> 「被比较的两者差得够多」，那这个差一旦随环境缩小，它就退化成一条恒真的断言 ——
> 这正是陷阱 87 的形状（判据依赖了一个没写进前提的环境条件），只不过这次的「环境」
> 是**档位**。

> ⚠️ **「从连上到第一块分片」这个读数，起点曾经取错了连接。**
> 页面同时开着**两条 WS**（预览 `/ws/preview` 与状态 `/ws/stats`），而**谁先连上是不确定的**；
> 第一版 `openAt` 取的是**先连上的那一条**，于是量出来的 `firstFragMs` 里混进了两条套接字
> 之间的时差（实测 `wsOpenSkewMs = +89 ms`）。修好之后同一个读数从 **280 ms 变成 119 ms**。
> 症状是**它看起来像产品慢**：一条「连上之后第一块分片多久到」的读数偏大，
> 没有人会去怀疑它的起点是另一条连接。
>
> 修法是把两件事**分开记**：`openAtAny`（任一条，只作诊断，回答「两条谁先连上」）
> 与 `openAt`（**专指预览那条**）；真正能抓到这类错的是一条**只判物理顺序、不判绝对值**
> 的断言 ——「画面第一次有内容不早于第一块分片」，它红了只有两种解释，插桩记错了时刻、
> 或者 `openAt` 取错了，**两种都是尺子坏了**。
>
> **判据：任何「从某个时刻起」的读数，先问那个时刻是从哪条流、哪条连接上取的**；
> 进程里同时开着两条同类型的通道时，「谁先」是一个随机量，不是前提。

> ⚠️ **同一条改动的两条断言，一条是确定的、一条是概率的 —— 变异检验必须以前者为准。**
> 「连上之后第一块分片 < 900 ms」这一条在变异下**不是每次都红**：关掉主动切分之后，
> 它量的那个数等于「连上的那一刻离下一个关键帧还有多远」，而**那是随机的** ——
> 恰好贴着关键帧连上就会量出一个小数（两次变异实测 **1208 / 1434 ms**，但那是运气，
> 不是保证）。**稳的是「分片间隔均值」那一条**：它把整段 **92 块**分片的间隔都平均了
> （开着 **222 ms**、关掉 **2001 ms**，**9 倍**）。
>
> 所以跑变异检验时**以均值为准，单次首分片只作佐证**；只有它红而均值绿，
> 说明的是「这次连得巧」，不是「改动生效了」。更要紧的是**没有均值那一条，
> 整块改动可以一行不生效而探针全绿** —— 关掉主动切分时 `meanPixelMs` 从 696 涨到 2171、
> 分片数从 92 掉到 11，而「尺子诚实」那两条**照样绿**（它们量的是页面那个数诚不诚实，
> 与分片节奏无关）。
>
> **判据：一条断言如果在变异下「可能」不红，它就不能单独用来证明「改动生效」** ——
> 检验要挑那条把整段样本平均掉的，它的失败不依赖任何一次抽样的运气。

> ⚠️ **「非关键帧开头的分片，浏览器收不收」这个问题只验了一半。**
> `MediaSource` 的 `sourceBuffer.onerror` 与 `<video>` 的 `readyState` 两条断言
> 在 **Blink（Chrome）上跑过、全部通过**；**Gecko（Firefox）那一半在这台机器上
> 验不了**（没装 Firefox），所以它是**未核实**，不是「也没问题」。这条边界没有
> 任何文档能替 —— 换一台装了 Firefox 的机器要补跑一次，在那之前界面上那句
> 「切碎了在某些浏览器上不出画」的提示照旧留着。

## 声音（音视频）

音频**默认关闭**（`audio.enabled = false`）。默认打开会改变每一台设备的 SDP，
而真实 NVR 的兼容性只能靠实测；开了之后 NVR 不接受，用户看到的症状是「加了音频
就没画面」，而归因会指向编码器。

- 两个源可以**同时开**：系统声音（WASAPI 环回）与麦克风，各自一个开关 + 一个
  增益。麦克风可以指定设备（`GET /api/audio/devices`，**空 = 用默认设备**）。
  设备列表随插拔变化，所以每次进页面现拉、不缓存。
- **音频是冷的**：改完要重开设备，所以段底给的是「保存并立即应用」
  （`POST /api/config` + `POST /api/reload`），按钮上写清代价 —— 录制会分段、
  RTSP 客户端会断开重连。
- **网页预览仍然没有声音**（`Fmp4Muxer` 是单流 + H.264 专用），用**电平表**
  代替：状态页上 `audio_level_l` / `audio_level_r` + `audio_state`
  （`off` / `ok` / `nosignal` / `error`）。这是取舍不是遗漏 —— 真要做就是第二条
  fMP4 轨 + MSE 的音频 `SourceBuffer`，工作量与风险都不小，而它换来的只是
  「不用开 NVR 就能试麦」。

> ⚠️ **`nosignal` 按设计不代表故障。** 「系统声音」这一路在**没人出声**时收不到
> 数据是正常的，而**安静有两种形态**：播放引擎停了（0 包）与引擎在转、每包全零
> （出包但不可闻）—— 两种都正常。正因为两种都是常态，**时间轴绝不能长在
> 「收了多少样本」上**：它由编码线程按视频拍数出来，源端不够就补零。否则系统一
> 安静，音轨就短一截。
>
> ⚠️ **第一次打开音频时给一句提示**：「若 NVR 取流异常，先关掉音频试试」。
> 默认关闭和这句提示是一起的，只做前一半等于把排查成本全推给用户。

## 重启服务与恢复出厂设置

两个都在网页上（`POST /api/restart` / `POST /api/factory-reset`），都在 Web 登录
之后 —— `/api/*` 本来就在登录之后，这两个接口不用新做鉴权。两者都必须**先回
202 再动手**：在 handler 里直接退进程的话响应永远发不出去，前端只会看到「网络
错误」然后自己重连，看起来像崩了。

**重启的三条代价**（按钮文案里就写着，不是一个干巴巴的「重启」）：

1. 中断当前录制并**分段**；
2. RTSP 客户端**全部断开重连**；
3. **所有网页会话失效、必须重新登录** —— 令牌签的是**每进程一份的随机密钥**，
   所以这不是 bug，是「重启」这件事本身的含义。前端把 401 解释成「服务回来了、
   请重新登录」，而不是「重启失败」。

按形态分流：**服务形态**退退出码 **7**，看门狗看到就原地重拉 ——
新进程在旧进程退出后由服务拉起，端口重绑的竞态因此不存在；**控制台 / 裸形态**
是 `CreateProcessW(自己, 原命令行 + --handoff 800)`，然后退 0，有大约一秒空窗。
新进程 bind 失败时**每 200 ms 重试、最多 5 秒**，失败报「端口被别的程序占了」
而不是静默死掉。

**恢复出厂**的 body 必须带 `{"confirm":"RESET"}`，**只认这一个字面量**，否则
400 —— 前端那个二次确认框是给人看的，服务端不信「我点了确认」。顺序固定：

1. `config.json` → `config.json.bak`（**先备份**，恢复出厂也是有人会后悔的）
2. 删掉 `config.json`
3. 清空两份日志：先 `Log::close_file()`（Windows 的 `fopen` 不带
   `FILE_SHARE_DELETE`，句柄开着就删不掉），再删 `desk2onvif.log` / `.old` 以及
   `logs\audit-*.log` 整个集合 —— 两组走**同一个** `is_our_log_file` 判据，
   **只删我们自己的文件、不递归删目录**
4. 设备时间偏移归零 + 名称复位
5. 走与 `/api/restart` **完全相同**的那条重启

> ⚠️ **恢复出厂恢复的是配置文件；命令行上带的参数照样生效。** 重启用的是同一条
> 命令行，所以 `--http-port 8080` 那一类会原样留着。真实安装形态
> （`packaging\start.ps1` 传的正好是默认值）因此确实回到 8080 / admin ——
> 但这是「命令行与默认值恰好一致」，**不是**「恢复出厂改了端口」。这句话要写在
> 确认框的文案里，而不是指望用户去读 README。

它**不碰**防火墙规则、不碰 `%APPDATA%` 以外的数据、不碰 `Temp\`。

## 版本号：一个来源，每次打包自增

版本号只有**一个来源**：`CMakeLists.txt` 里 `project(Desk2ONVIF VERSION x.y.z)`
那一行。同一个 `PROJECT_VERSION` 喂给三处：

- exe 的 `VersionInfo`（`resources/desk2onvif.rc.in`，由 `configure_file` 生成）；
- 运行期宏 `D2O_VERSION`（`--version` 打一行 `Desk2ONVIF x.y.z`，`/api/status`
  的 `version` 字段，侧边栏 footer）；
- `scripts\package.ps1` 的包名与 `firmware_version`。

也就是说这个项目里有**四**处会显示版本号，而它们全都从那一行来。这不是靠注释
保证的：`verify_installer.ps1` 与 `verify_portable.ps1` 里各有一条**三方一致**
断言（包名 == exe 的 `VersionInfo` == `/api/status` 的 `version`）盯着。

> ⚠️ 这条注释以前是**假的**：`package.ps1` 里写着"三处必须一致"，而 exe 自己的
> `VersionInfo` 是**硬编码的 `0.1.0`**，压根没接上 —— 正是那段注释宣称要防的
> 漂移。一般化：**一条"我保证 X 一致"的注释是一句承诺，不是一个检查**；
> 能自动对账的就去对账。

- **每次打包都 +1**（`package.ps1` 默认把 patch 位加一，**不管内容变没变**）。
  这是用户明确选的规则：好处是「我装的到底是哪一版」永远有唯一答案，代价是连打
  两次（内容一字未改）也会 +1。
- `-NoBump` = **原样重打**，不自增。
- `-NoBuild` 与自增**互斥**：`-NoBuild` 打的是上一次构建出来的 exe，自增会让包名
  和 exe 的 `VersionInfo` 对不上，所以 `-NoBuild` 且没给 `-NoBump` 时**直接报错
  退出**，消息里写清两条出路。

```powershell
scripts\package.ps1                      # 自增 + 重新构建 + 打包
scripts\package.ps1 -NoBump              # 版本不动，重新构建 + 打包
scripts\package.ps1 -NoBuild -NoBump     # 原样重打刚才那一版
```

## 设备身份：哪三个字段锁死了，逃生门在哪

设备信息页（`/info`）上，**硬件 ID / 序列号 / 设备 UUID** 三行是**真的 `disabled`
输入框**（不是"看起来是灰的"——那是两回事，只有 `disabled` 是浏览器层面的事实，
点不动、选不中、提交不上去）。其余几个 —— 厂商、型号、固件版本、设备名、
位置 —— 照旧可改。

**为什么锁**：序列号是 NVR 认设备的依据。用户（或一次手滑、一次批量粘贴）
把它改掉之后，NVR 那边是"多出来一台新设备、老的那台不见了"—— 而录像、看板、
告警规则都挂在那台"老设备"上。设备 UUID 同理，它还被 ONVIF 的
`GetSystemDateAndTime` 之外的几个地方当作设备身份报出去。硬件 ID 是**硬的**
（"这台机器是什么"），本来就不该在网页上改。

**锁在界面与 API 两层**（前端禁用 + 后端 `apply_config` 里无条件回灌），
不是只把输入框改成只读 —— 只做前端的话，一次 `curl` 就绕过去了。`web_contract.py`
里两只手都握着：改这三个字段的值**不变**且回应里有说明，同一批里改
`model`/`device_name` **确实变**（反面对照，否则"全都不变"也能全绿）。

**逃生门是手改 `config.json`**（停下程序、改文件、再启动）。这是刻意的：
镜像克隆的机器会共用一套派生出来的身份（`MachineGuid` 被一起克隆走了），
那时用户需要一个出路。所以准确的说法是**锁在"界面与 API"，不在"文件"**。

> ⚠️ **"版本号"有两个，别混**：`/api/status` 的 `version` 是**程序真实版本**
> （只读，见上面「版本号」那节），`onvif.firmware_version` 是**报给 NVR 的值**
> （可改，也是安装包里那个版本）。界面上这两处必须分开写 —— 长得像的话，
> 看起来永远像其中一个坏了。

## 操作日志（审计）

调试日志（`desk2onvif.log`）回答的是"**程序**刚才干了什么"；操作日志回答的是
"**谁**在什么时候改了这台设备"。用户点名的三件事 —— 改码率、摄像头改名、对时
—— 网页上和 NVR 侧改的都记，登录成功/失败也记。

| | 调试日志 | 操作日志 |
|---|---|---|
| 落在哪 | `<配置目录>\desk2onvif.log`（+ `.old`） | `<配置目录>\logs\audit-YYYY-MM-DD.log`，**一天一个文件** |
| 留存 | **4 MB 轮转**，只留一份 `.old` | **默认 180 天（半年）**，启动时剪一次枝 |
| 怎么关 | —— | `--no-audit` / `log.audit=false`；`--audit-keep-days 0` = 不剪枝 |
| 记什么 | 逐秒状态、警告、错误 | **改动类 + 登录**；不记查看类（开页面、看快照、读配置） |

**「半年留存」说的是操作日志这一份，不是 `desk2onvif.log`。** 后者仍然是
4 MB 轮转 —— 一条每秒都在写的调试流按天留半年是几百 MB，那是两回事。

一行长这样（时间 / 来源 / 身份 / 动作 / 细节，五段，段间是 ` | `）：

```
2026-10-08 15:30:12 | 192.168.1.23 | web:admin | config.set | 已生效[onvif.password] 待重启[capture.bitrate_kbps]
```

> ⚠️ **第一段那个时间用的是主机时间，不是设备时间。** `audit_log.cpp` 取的是
> `std::time(nullptr)`，而"设备时间"是主机时间**加**上 NVR 下发或手动校准出来的
> 偏移（见上面「时间」那一节）。所以**审计里那行时间与画面水印上那个时间可以差出
> 几分钟甚至几小时**，NVR 对过时之后尤其明显。这不是不一致，是两把尺子量两件事：
> 审计回答"这台**机器**什么时候被谁改了"，水印回答"这段**录像**对应录像机时间轴的
> 哪一刻"。要对账录像请用水印/`GetSystemDateAndTime`，要排查操作请用审计。

**口令、`Authorization` 头、nonce、token 永远不会出现在里面。** `config.set`
那条**故意只记字段名、不记值** —— 字段名不是值，躲开的是整类问题。这不是
一句放着的注释：验收脚本里有一条硬断言盯着它，拿四个真口令（网页口令 / ONVIF
口令 / 本次改过去的新口令 / 登录失败那次填的错口令）在整份日志里搜，必须**零
命中**，同时四个正面控制串必须找得到（否则"找不到口令"和"根本没读到文件"在
报告上长得一模一样）。

**恢复出厂设置会清空它**（和调试日志一起）。执行的顺序里留了一手：先记下
"谁恢复的出厂"，清空之后再有一行新的 `startup` 从这一秒开始写 —— 所以
`logs\` 目录不会空着，也不会留下恢复出厂之前的内容。删的是
`audit-\d{4}-\d{2}-\d{2}\.log` 这个**集合**（与剪枝共用同一个判据），目录本身
留着，别的文件一个不碰。

界面在侧边栏「设备 → 操作日志」（`/logs`）：只读、倒序、按天分组、可按关键字
过滤、可复制一行，顶部一行写着留存策略与当前占用（"保留 180 天，共 N 个文件 /
M KB；恢复出厂会清空"）。

> ⚠️ **`--no-audit` 会被后续任何一次保存带回磁盘。** 命令行那两项是**折进
> `cfg`** 的（与 `--no-onvif` 折进 `cfg.onvif.enabled` 是同一条规矩）：
> `GET /api/config` 报的必须是**生效值**，否则配置里写着 `audit: true` 而一行
> 日志都不写，界面上看着一切正常。代价就是这一条 —— 想长期关掉它，改配置文件
> 里的 `log.audit` 或网页上那一项，而不是只在命令行上加一次。
>
> 审计写不出来（目录建不了、盘满了）**不会让程序起不来**，但会当场打一条 WARN，
> 而不是安静地继续跑。一个以为自己在被审计的系统，比一个知道自己没被审计的
> 系统危险得多。

## 两路码流（主码流 + 子码流）

主码流是桌面原分辨率，子码流是同一画面缩到 `--sub-height`（默认 360），
两条各自独立的 x264 实例、各自独立的 RTSP 路径（`/live` 与 `/live_sub`）。

**为什么默认就开**：NVR 的多画面网格默认拉的是**主码流**。16 路网格就是同时
拉 16 条全分辨率的流 —— 编码端 CPU 是 16 倍，网络也是 16 倍。开着子码流，
网格走子码流、点开单画面时 NVR 才切回主码流，这是它唯一的作用，也是所有
真实摄像机都这么干的原因。

```powershell
.\build\bin\desk2onvif.exe --rtsp --sub-height 360 --sub-bitrate 512   # 默认就是这样
.\build\bin\desk2onvif.exe --rtsp --no-sub                             # 只推主码流
```

ONVIF 侧它是**第二个 profile**：`GetProfiles` 返回 `main` 和 `sub` 两个
（token 就是这两个名字），各自带自己的分辨率；`GetStreamUri` 按 token 给
各自的地址。NVR 添加通道时选哪个 profile，就拉哪一路。

> 子码流的默认值是**开**，这一点值得留意：它意味着默认情况下 CPU 占用比
> 「只编一路」高。不给 `--rtsp` 时它不产生任何开销（没有消费者就不编）。

## 多通道：一块屏一路，摄像头也能加进来

**默认行为就是多路。** 启动时枚举显示输出，每一块**能抓**的屏自动成为一路；
一块屏都没有变化时（绝大多数机器只有一块屏）行为和从前**逐字节相同**。

| | 通道 1 | 通道 N（N ≥ 2） |
|---|---|---|
| 谁建它 | 老路径：`capture.*` / `rtsp.*`，也就是今天文档里写的这一路 | **自动发现**：显示输出各一块，编号接在显式配置的通道之后 |
| 分辨率/帧率/码率 | 命令行与 `capture.*` / `rtsp.*` | `channels.items[]`，缺省档位是「流畅」 |
| ONVIF 设备服务 | `web.port`（8080） | **`web.port + N`** —— 通道 2 在 8082、通道 3 在 8083 |
| 主码流 RTSP | `rtsp.port` + `rtsp.path`（554 / `/live`） | 同一个 `rtsp.port`，路径默认 `/chN`（`/ch2`、`/ch3`…） |
| 子码流 RTSP | `/live_sub` | `/chN_sub` |
| 录像文件 | `--record` 给的那个名字 | 同一个名字加 `-chN` 后缀 |

**为什么 ONVIF 每路要一个端口，而 RTSP 不用**：RTSP 的请求行里带着路径，
一条连接上来就知道说的是哪一路；ONVIF 的设备服务**没有这个信息** ——
`GetDeviceInformation` 就是一个没有参数的 SOAP 请求。所以"这台机器有几台设备"
只能靠端口区分。代价是每路占一个端口，且 **8081 是空着的**（端口差是 `N`，
不是从 8081 顺排）。

每路的 ONVIF 身份（型号、序列号、设备 UUID）都不同，否则 NVR 会把它们当成
同一台设备。序列号与 UUID 由本机标识（**主机名 + 注册表里的 `MachineGuid`**，
`src/onvif/net_identity.cpp`）**加通道号派生**，所以重启不变、换网卡不变 ——
MAC 集合从第五轮起**不参与**派生（插拔网卡、扩展坞、禁用虚拟网卡都会改它）。

### 摄像头：加一路看看有没有画面

```powershell
.\build\bin\desk2onvif.exe --list-cameras          # 列出本机摄像头（Media Foundation）
.\build\bin\desk2onvif.exe --camera "FHD Camera" --rtsp --http
```

`--camera` 把**通道 1** 换成摄像头。它后面接的是名字或者符号链接（`--list-cameras`
会打出来）。通道 1 一旦不是显示器，那块屏就不再被跳过 —— 于是自动发现会把
**所有**能抓的屏各建一路（上面那条命令在这台机器上得到 2 路：摄像头 + 屏）。

摄像头通道**不会自动建** —— 一台机器可能有三个摄像头，全给你接上去是替用户
做决定。所以它只从显式配置来：网页「配置 → 通道 → 检测到的源」里点摄像头那一行
的**「加为通道」**，或者手写 `channels.items[]`（`"source": "webcam", "camera": "FHD Camera"`）。

摄像头走 **Media Foundation**，和桌面的 DXGI 是两套采集（`src/capture/webcam_capture.cpp`）。
格式请求里**故意不写尺寸、也不写帧率**（只写"我要 RGB32"），拿到什么由摄像头决定 ——
那些档位是摄像头特有的，替它选等于猜。所以配置里写 30、而摄像头实际给的是别的数，
是常态而不是故障：**实际值看状态页**，那里报的是协商之后回读的值。

窗口捕获（"把某个应用程序当一个通道"）**这一轮没做**，留下的接口是 `source` 字段：
现在已经认 `display` 和 `webcam` 两个值，再加一个值就是下一轮的事。

### 关掉自动建出来的某一路

给那块屏**写一条显式的通道项、然后把 `enabled` 去掉**。自动发现会跳过"已经被显式
项认领的屏"，**不管那条项是开还是关** —— 这就是"我不想录第二块屏"的表达方式，
不用去改什么全局开关。停用的项不会从界面上消失，它在**设备信息页**的通道列表里
显示成状态「已关闭」；而如果它是**建不出来**（同一块屏被前一路占了、摄像头名字
匹配不上、那块屏根本抓不了），状态那一栏写的是「未启用：<原因>」，原因整句照印。
两种"没跑起来"必须分开写：都写"已关闭"的话，用户会去配置里找一个**明明是开着的**
开关。

上限是 **8 路**（`ChannelsConfig::kMaxChannels`）。超出的部分会被截掉并在
`/api/config` 的回应里给一条说明，**不会**静默丢弃，也不会重新编号。

改 `channels.*` **要重启**才生效（端口、UUID、RTSP 路径都得在启动时定死）。
改完保存时响应里的 `pending` 会逐字段列出来。

### 每通道各录一份

`--record out\mc.mp4` 在多通道下是 `mc.mp4`（通道 1）+ `mc-ch2.mp4` + `mc-ch3.mp4`……
每一路自己一个编码器、自己一个 MP4、自己一套分段（换分辨率时 `mc-ch2.1.mp4`）。
文件名规则的两条要点：**不给 `--record` 时一路都不录**（不会凭空造出 `-chN.mp4`），
以及**通道 1 的文件名和单通道时完全一样** —— 老用户的脚本、看板、清理任务不用改。

**磁盘占用摆到界面上**（设备信息页 →「录像占用」）：每一路的文件名、当前大小、
以及按码率粗算的"每小时约多少"。这一列是**估算**，用的是配置里的码率；桌面静止
的时候实际写入会远小于它（DXGI 在画面没变时可以不产帧），所以文案里写的是"约"。
要看准的看左边那列实际大小。8 路全开、每路 2 Mbps 是**每小时约 7 GB** ——
数字摆出来，而不是等磁盘满了才发现。

### 预览页为什么一次只看一路

预览页顶上有个通道选择器，**点一次换一路**，不是多画面宫格。这不是省事：

- 每多推一路，编码是**已经在跑的**（NVR 在拉），但**推给浏览器的**那一路要额外
  走一段 fMP4 封装 + WebSocket；
- 更要紧的是**读数**。页面上的「真实延迟」是拿"帧进编码器的时刻"和"浏览器解码出
  来的时刻"相减算的，两路混在一个页面上，这个数就同时指着两条管线 —— 它不再
  回答任何一个问题。

所以选择器换的是**整个页面的那一路**：旧连接关掉、`POST /api/preview-channel`
翻后端的状态、新连接建立。后端只把「当前那一路」的分片推给浏览器
（`preview_hook` 里一个 `id == active_channel` 判断），`/api/snapshot.jpg` 也跟着翻。

> **切的顺序是刻意的：先关旧的 → 再 POST → 最后开新的。** POST 那一下后端会把
> 新那一路的**初始化段重放**一遍，而重放是广播给所有连接（WebServer 只留最近
> 看到的那一份 moov）。旧连接还在的话，就会在一条正在跑的 MSE 流中间收到
> 另一路的 moov。这一条已经用变异检验验过：**把后端那次重放去掉，探针唯一变红
> 的就是"切换后解码尺寸变成了通道 2 的"** —— 去掉之后不报任何错，画面只是黑着。

### NVR 那边会看到什么

WS-Discovery 一次会报 **N 条 ProbeMatch**（N 路）。有些 NVR 按 IP 归并，于是
"明明有三路，只搜到一台"。退路是**手工添加**每一路：

```
http://<本机IP>:8080/onvif/device_service     # 通道 1
http://<本机IP>:8082/onvif/device_service     # 通道 2
http://<本机IP>:8083/onvif/device_service     # 通道 3
```

凭据是 `onvif.user` / `onvif.password`（和通道 1 同一对）。

### 一块屏不能开两路

DXGI 的桌面复制在**一块输出上同时只允许一个** `IDXGIOutputDuplication` 对象，
第二个 `DuplicateOutput` 直接失败，报的是 `E_INVALIDARG` —— 从"参数非法"这四个字
里读不出"你把两块屏写重了"。而且谁先谁后是线程赛跑，不拦的话症状可能是**通道 1
红掉并带崩整个进程**。

所以写重了不会去"抢"：第二条指向同一块屏的项保持 `enabled=false`、带一句
`blocked_reason`，界面上显示成"建不了"并原样念出原因。

这条限制**只管显示器** —— 它是 DXGI 的规矩，摄像头不走那条路。两个通道指同一个
摄像头不在拦截范围内，能不能同时打开取决于那个摄像头的驱动（很多允许，有些
不允许）。**这一条没有实测过**：本机只有一个摄像头，凑不出这个场景。

### ⚠️ 音频这一轮只跟通道 1

`RtspOptions::audio` 是**单数**的，它的 sink 挂在通道 1 那个
`ServerMediaSession` 上。也就是说多通道下音频是**结构性缺失**的，不是"忘了接"。
代价落在最想要麦克风的地方（摄像头那一路），所以这里明说，而不是藏着 ——
通道 2 起的配置里**不给**音频开关，免得给一个按了没反应的按钮。
补齐的规模大约 80 行（`AudioTrack` 改成 vector、`push_audio_au(channel, …)`、
`RtspOptions::audio` 改成 vector），留下一轮。

## 画面里的鼠标指针

**桌面复制给出的画面里没有鼠标指针。** DXGI 把指针单独交出来：位置和可见性在
帧信息里，形状要另外用 `GetFramePointerShape` 取。所以「录出来的视频里没有
鼠标」不是 bug，是 DXGI 的默认行为 —— 而对一个要冒充摄像机的桌面流来说，
看不见鼠标就等于看不见人在做什么。这个项目把它合成了回去（`src/capture/
cursor_overlay.h`），三种形状各自的绘制规则是**从 Windows 的 DDB 语义推出来的**：

| 形状 | 规则 |
|---|---|
| 彩色 | 逐像素按自己的 alpha 混合 |
| 掩码色 | `alpha == 0` 表示**反相**（`dst.rgb ^= src.rgb`），Windows 10 的反色指针走这支 |
| 单色 | 1bpp，高度是实际的两倍（上半 AND、下半 XOR）；先 SRCAND 再 SRCINVERT，**顺序不能反** |

还有一条容易忽略的：桌面静止时 DXGI 不产出帧，而"鼠标动了"是**独立于画面更新**
的另一种帧来源。那一类帧里的桌面纹理是**未定义内容**（DXGI 只在画面变了才更新
它），所以指针必须画在那份"上一次的完整桌面图"上，而不是重新去读纹理。

> `--list-displays` 与 `--selfcheck` 都不动鼠标。真要端到端验指针，用
> `tests\cursor_harness.ps1`（它会开一块纯色全屏画布并**驱动鼠标**走一条固定
> 路径）—— 那一条会真的动你的鼠标，别在远程操作时跑。

> `audio_mixer_check.cpp` 的 `[4]`/`[5]` 原本是「先量一遍增益 1.0（`[3]` 那一窗）、
> 再量一遍增益 0.5、除一下」，于是比值成了 **0.369 / 0.522**（期望 0.500 / 0.7071）。
> **数落在区间外、失败信息指向「增益没乘对」，而增益那一行一个字节都没错。**
> 三条独立的测量把它钉死在**环境**上，没有一条靠推理：
> **(a) 比值本身是精确的** —— `[6]` 的谱线给出稳态 `0.2035`（峰值/有效值 = 1.417 ≈ √2，
> 干净正弦），而 `[4]` 的 0.1017 = **恰好** 0.5 × 0.2035、`[5]` 的 0.1439 = **恰好**
> 0.7071 × 0.2035，也就是说乘法和 1/√2 都**逐位正确**，错的只有作为分母的那个窗口；
> **(b) 在采集边界上分开** —— `wasapi_check.cpp` 的 `[2]`（进程里没有任何混音器的裸
> `WasapiCapture`）读到同一个 0.8936 / 0.2755，**环回层就有了**，与混音器无关；
> **(c) 形状** —— 一个只测 `WasapiCapture`、每 40 ms 打一行的探针给出：起播前是整块整块的
> 纯静音（峰值 `0.0000`），起播后 0.8936 → 0.8450 → 0.3617 → … **单调平滑**衰减到
> t≈4.36 s 起的岩石般稳的 0.2032/0.2033/0.2034，全程 crest = √2，零丢弃零重开。
> **结论：这台机器的渲染端点在冷引擎起播时有一段约 3.2 秒、约 1.78× → 1.0× 的增益斜坡，
> 我们的采集忠实搬运、混音器原样透传 —— 产品是无辜的，缺陷在测试的尺子上。**
> 斜坡是**冷引擎专属**的（键在「引擎闲置过」上，不在「每次起播」上）。
>
> **做法（这是本条的重点）：把绝对测量改成差分测量 —— 两个 `AudioMixer` 用只差一个变量的
> 配置并排启起来，在同一个 40 ms 拍里各 `fill()` 一次，端点给的是同一份（随时间变的）增益，
> 于是它在比值里精确约掉。** 这比「等它稳了再量」更强：**它不需要对「要等多久」做任何假设**，
> 连「有没有斜坡」都不需要知道。实测两个比值分别是精确的 **0.5000** 与 **0.7071**，
> 而且两次都**在斜坡里面**测的（0.3451/0.1725、0.4343/0.3071 都远高于稳态 0.203）——
> 所以这是真的约掉了，不是碰巧。斜坡本身**只报告、不判**（它是这台机器端点的行为，
> 不是混音器的契约），但要印在日志上，否则下次看到两个不一样的峰值又得从头查一遍。
>
> **变异检验（三处，各自只弄红它自己那一条，别的一条都不动 —— 这才是「它们在分辨不同的
> 东西」的证据）：** `dst[i] +=` 改成 `dst[i] =` ⇒ **恰好 2 条红，全在 `[5]`**，
> `[3]`/`[4]` 全绿（单源时 `=` 与 `+=` 是同一件事 —— 正是文件头那句
> 「只有两路同开才露馅」的正面证据）；`headroom = 1/√n` 改成 `1.0f` ⇒ **恰好 1 条红**
> （`[5]` 的峰值比 1.0000），`[4]` 绿（单源 headroom 本来就是 1.0）；
> `g = gain * headroom` 改成 `g = headroom` ⇒ **恰好 1 条红**（`[4]` 的峰值比 1.0000），
> `[5]` **绿**（那两路 `gain` 都是 1.0，它看不见增益被丢掉这件事）。
> 三次都从基线逐字节还原（`[RESTORED] 23/0/0`），且这次是直接 `g++` 编译、不经过 ninja，
> 所以没有「拷贝保留 LastWriteTime ⇒ 不重编」那个老坑 —— 但仍然每次都断言
> 「exe 的 mtime 前进了」，因为**「变异之后仍然是绿的」和「根本没重编」在报告上长得一样**。
>
> ⚠️ **诚实边界**：`[4]` 那条「并排两路都接到了信号」是**前提断言**，它的红路径
> （第二个环回客户端静默拿不到数据）是环境条件，**测试自己造不出来**；
> `[5]` 那条不一样，它会被第一种变异弄红。所以前者只能报成「当前通过并打印了两个峰值；
> **未经独立的变异验证**」。
>
> **两条判据：** **(i)** 凡是「除以一个早先量出来的绝对值」的比值断言，先问一句
> **分母是谁产出的** —— 是产品，还是这台机器当时的某个绝对电平？后者就得改成
> **同一时刻的并排差分**，让机器的贡献在比值里约掉（这是陷阱 87 的解法换了个入口：
> 87 是判据的**宾语**错了，这条是判据的**分母**错了）。
> **(ii)** 一组变异里，**每一条断言都应当有一个能单独把它弄红的变异**；
> 三条变异各红各的、互不牵连，才说明那几条断言在分辨不同的东西。

> **（新，99，2026-10-08，同一轮）一条「两条路对同一个量必须报同样的值」的断言，
> 如果那个量是单调递增的计数器、而两次取样之间隔着几十毫秒，那它量的是时间，
> 不是一致性。** `tests\web_contract.py` 的 `[4]` 段把 `GET /api/status` 与
> `WS /ws/stats` 两条路的字段逐一对账（第二轮 `perf_*` 那批就是被它逼着落到
> 两条路共用的那个补丁点上的）。原写法是：先 GET 一次拿到 `s`，再读 WS 的首帧
> `ws_j`，然后 `k != "ws_clients" and ws_j[k] != s[k]` 就是不一致。
> **而这条链上有两根「没人看也在走」的计数器**：`preview_fragments` /
> `preview_fragments_unwatched`（分片节奏）与那个 1 Hz 的 stats 块。两次取样
> 间隔里它们**合法地**往前走一格，于是这条断言报出来的是「你两次读的时间不一样」。
>
> **量出来的（同一二进制、同一批取样、两条规则并排）**：
> `out\t-regress\counter-race-probe.py` 把 `[4]` 那段原样重放 300 次，
> **旧规则 11/300 次红、新规则 0/300 次红**；取样间隔 `min 0 ms / 均 7 ms /
> max 16 ms`；红的那 11 次的字段签名只出现两种（**9 次**是 `preview_fragments`
> 与 `preview_fragments_unwatched` 同时翻，**2 次**是那个 1 Hz 的 stats 块 ——
> 一次带 `osd_refresh_frames`、一次带 `keyframes`），与「计数器在两次取样之间
> 走了一格」完全对得上。**并排量同一批取样是有意的**：两条规则吃的是同一组数据，
> 所以「旧 11 次、新 0 次」这句话里没有第二次测量的运气。
> ⚠️ 那个 1 Hz 块的签名在延时档位（Phase W）之前就该出现 —— 它证明这个缺陷
> **早于**这一轮，不是新引入的。
>
> **落盘凭据**：`out\t-regress\counter\probe.txt`（3638 字节，UTF-8 无 BOM）是探针
> 自己那份输出，同目录的 `run.log` 是同一次服务端的逐秒日志，
> `out\t-regress\counter-run.txt` 是外层 `.ps1` 的完整 stdout。
> **这三份是先落盘、后写进报告的。** 上一版 `counter-race-run.ps1` 只 `Write-Host`，
> 于是「旧规则 9/300 红」这句话在盘上没有任何凭据 —— 跑过的读数事后既无法复核
> 也无法被质疑。判据：**一个数只要会被写进报告，它就得先落在盘上。**
> **两轮跑分别是 9/300 与 11/300**，这不是矛盾，而是这条论断的正面证据：它本来
> 就是一场竞速，红几次取决于那 300 次取样恰好撞上几个「计数器在间隔里翻了一格」
> 的窗口（两轮的间隔也不同：均 6 ms / max 12 ms 对 均 7 ms / max 16 ms）；
> 而**新规则两轮都是 0/300** —— 那个 0 才是这条断言要拿到的东西。
>
> 修法是把判据从「两次取样必须相等」换成「**只比两次取样之间没变过的字段**」：
> 再 GET 一次 `/api/status` 得 `s2`，`stable = {k | s2[k] == s[k]}`，只在
> `stable` 上比。实测 `len(stable) == 58`，并加了 `len(stable) >= 25` 的守卫。
>
> **变异检验（陷阱 85 的纪律）**：`out\t-regress\wc-run.ps1` 拿**盘上那份真的
> `tests\web_contract.py`** 打一个私有后端（Web 8141 / RTSP 8573）——
> `wc-baseline.txt` **192/0**（`两次取样之间没变过的字段有 58 个 ≥ 25`）；
> 在 `web_server.cpp` 的 `patch_live_counters(j);` 与 `last_stats = j.dump();`
> **之间**（在那把 `mu` 锁里面）插一句 `j["preview_ready"] = false;`、重编 →
> `wc-mut.txt` **191/1**，**恰好一条红**：
>
> ```
> [FAIL] 稳定字段在两条路上的值一致
>          不一致: ['preview_ready']
> ```
>
> 而同一段的字段集合相等、`>= 25` 守卫、第二次 GET 三条**全绿**；从
> `out\t-regress\web_server.cpp.before-t4-mut`（SHA256 `604B4270…3940A`，
> 102183 字节）逐字节还原 → `wc-restore.txt` **192/0**。**这一跑的要点是
> 「抄件绿了说明不了原件绿了」**：探针只是把判据抄了一遍，它证明的是「这个判据的
> 形状是竞速的」；「盘上那份真的不再红」只有拿盘上那一份跑出来才算数。
> ⚠️ **诚实边界**：新加的 `len(stable) >= 25` 守卫，它自己的**红路径**（字段全变成
> 不稳定的、`stable` 收缩到 0 时应当红）**没有**被独立变异验证过 —— 上面那条变异
> 只会把它**绕过**，不会把它弄红。与第 92 条 `[4]` 那条「并排两路都接到了信号」
> 的前提断言是同一类，只能报成「当前通过、未经独立的变异验证」。
>
> **判据**：一条断言只要它的两个操作数是**两个时刻的快照**，就先问一句
> **「这两个时刻之间，这个量允许变吗」**。允许变（单调计数器、速率、内存占用、
> 连接数 —— 凡是「随时间走」的量）就必须改成**差分/稳定性**判据，而不是相等
> 判据；而「改成稳定性判据」之后**要留一条守卫防止它退化**（样本收缩到 0 时恒真
> —— 陷阱 91 那个空转的绿，只是换了个入口）。这一条与陷阱 87（判据依赖环境）、
> 88（判据依赖时间点）是同族的第七种形状：87 依赖**机器状态**、88 依赖
> **会话年龄**、这条依赖**两次取样之间的墙钟**。

那个 `[1]` 里"两路必须是两个不同的尺寸"不是凑数的断言：两路尺寸相同就说明
子码流其实没编，只是把主码流又推了一遍 —— **而那样表面上一切正常**。
`[1]` 读帧率的方式同样有来历：它原来硬编码 `30/1`，于是默认值从 30 改成 25 的
那一刻，**两条断言当场变成假失败**（产品一行没错）。现在它是拿
`/api/config` 里那个数去比服务自己报的数。

`[4]` 读数和 `[1]` 不是同一段：`[3]` 段里的画质档位往返会 POST 一份新配置并

**换分辨率那一路的判据和换刷新率那一路是相反的**，因为产品的行为就是相反的：
尺寸没变时原地重建捕获会话、接着录同一个文件；尺寸变了则整条链重开，于是
文件分成三段、RTSP 服务在同一个端口上重开两次（`SO_REUSEADDR` 那条路——
以前只是"应该能用"，这里是实测）。拿同一组断言去卡两种行为，多出来的就是假失败。

相对秒排的时刻全部作废，而程序是数拍数计时的 ⇒ 它的墙钟总时长 = 挂起时长 +
`--seconds`。这一趟的结果（`-Seconds 200`，实际跑了 10 分半）：

```

```powershell
# 1. 供给依赖（三个都幂等，重复跑无副作用）
.\scripts\fetch_ffmpeg.ps1
.\scripts\build_live555.ps1
.\scripts\fetch_uvcpp.ps1      # 只搬运；库本身要先按 third_party\README.md 编好

# 2. 构建 + 自检
.\scripts\build.ps1
```

`build.ps1` 会配好 PATH、配置、编译、部署运行期 DLL，最后跑一遍自检。
**建议直接用它，不要手敲 cmake** —— 原因见下。

> ⚠️ **`build.ps1` 不构建网页。** 它只管 C++；`web\dist` 是 `web\` 目录下另跑
> 一次 `npm run build` 出来的（`vue-tsc --noEmit && vite build`）。两者之间
> **没有任何依赖边** —— 改完 `.vue` / `.ts` / `.css` 不重编，程序照跑、`/` 照开，
> 只是发给你的是**上一次**的界面，而没有任何地方会说这件事。
> `tests\browser\*.mjs` 那批探针量的正是 `web\dist`，不是 `src` —— 所以改完前端
> 先建、再跑探针，顺序反了红的是上一次的产物（陷阱 91）。
>
> ```powershell
> cd web; npm ci; npm run build; cd ..
> ```

> 如果 `desk2onvif.exe` 正开着，链接会因为**文件被占用**而失败。脚本会告诉你
> 是谁占着，并给出 `.\scripts\build.ps1 -StopRunning`（它会**直接终止**那些进程，
> 不打招呼、也不等它写盘）。

<details>
<summary>手工调用 cmake 的等价命令</summary>

```powershell
# PATH 必须前置 msys64\mingw64\bin，否则编译器会以一种完全静默的方式失败
$env:PATH = 'C:\msys64\mingw64\bin;' + $env:PATH

cmake -S . -B build -G Ninja `
  -DCMAKE_BUILD_TYPE=Release `
  -DCMAKE_C_COMPILER=C:/msys64/mingw64/bin/gcc.exe `
  -DCMAKE_CXX_COMPILER=C:/msys64/mingw64/bin/g++.exe `
  -DCMAKE_MAKE_PROGRAM=C:/msys64/mingw64/bin/ninja.exe
cmake --build build -j
```

</details>

> **为什么不能直接用普通的 PowerShell 敲 cmake。**
> MSYS2 的 `gcc.exe` 自己能启动（它在 `mingw64\bin` 里，DLL 走"同目录优先"），
> 但它调起来的 `cc1.exe` 在 `lib\gcc\...\15.1.0\` 下 —— 那里没有任何运行库 DLL，
> `cc1` 只能靠 PATH 找。PATH 里没有 `mingw64\bin` 时，`cc1` 会从别处（例如某个
> 自带 `zlib1.dll` 的程序目录）加载到版本对不上的同名 DLL，然后以
> `STATUS_ENTRYPOINT_NOT_FOUND` 退出。这个失败**完全静默**：`cc1` 一个字都不打印，
> CMake 报的是 "The C compiler is not able to compile a simple test program"，
> Ninja 那边只有一行 `FAILED: [code=1]`，没有任何字样指向 PATH。
>
> `CMakeLists.txt` 里对这个情况有显式检查，会直接说明原因；
> 但 `build.ps1` 更省事 —— 它一开始就把 PATH 配好。

## 打包

```powershell
.\scripts\package.ps1 -Zip                  # 安装包 + 绿色版 zip，都进 release\
.\scripts\package.ps1 -NoBuild              # 只用现有产物重新打包（改的只是打包脚本时用）
.\scripts\package.ps1 -AppUrl https://...   # 把项目主页写进安装程序的信息里
```

产出两个交付物，**装出来的文件完全一样**，只是分发方式不同：

| | 产物 | 说明 |
|---|---|---|
| 安装包 | `release\Desk2ONVIF_Setup_<版本>.exe` | Inno Setup 简体中文向导，装到 `%LOCALAPPDATA%\Programs\Desk2ONVIF`，**不弹 UAC** |
| 绿色版 | `release\Desk2ONVIF-<版本>-win64.zip` | 解压即用，整个目录拷走就能换机器 |

版本号只有 `CMakeLists.txt` 一个来源，由脚本传进 `.iss`；不传 `-AppUrl` 时安装程序里
**不显示**发布者链接（以前那里是个指向 GitHub 首页的占位符，比没有链接更糟）。

两个交付物各配一份**脚本化的验收**，动过打包相关的东西之后跑一下：

```powershell
.\scripts\verify_installer.ps1     # 47 项：真装一遍、真跑起来、真卸干净
.\scripts\verify_portable.ps1      # 53 项：解到空目录、走 start.ps1 跑、验完删掉
```

它们不是"双击一下看着能装"的替代品，而是逐条断言：装下来的文件清单、**exe 里到底
有没有图标和版本资源**（这个 `ExtractAssociatedIcon` 查不出来，见陷阱 56）、配置里的
口令带着引号和反斜杠能不能原样往返、`web\dist` 在不在（少了它程序照跑、只有一个字
都不报的白屏）、起服务后前端契约过不过、卸载是不是一点不剩。绿色版那份还额外验
`.ps1` 必须带 BOM 而 `.bat` 必须没有、`start.ps1 -Portable` 的配置落点、
以及**目录之外不该多出任何东西**。

⚠️ **两台都要看"卸载/清理之后还剩什么"，而这一条在第四轮真的红过。** 操作日志
（`{app}\logs\audit-*.log`）是**运行期**才出现的文件，不在 Inno 的安装清单里，
`[UninstallDelete]` 一开始没声明它 ⇒ 卸载把 `config.json` 删掉、把 `logs\` 留下 ⇒
`{app}` 不空 ⇒ 目录本身也不被移除。症状是"卸载完了还剩一个目录，里面一份配置加一份日志"。
修法是 `Type: filesandordirs; Name: "{app}\logs"`（`filesandordirs` 而不是 `files` ——
目录本身也得删），改完 `verify_installer.ps1` 从 **46 通过 / 2 失败** 变成 **47 通过 / 0 失败**。
**绿色版那一份照不出这一类**（它靠 harness 删临时目录，只有安装包这一路会留下痕迹），
所以两个都绿 ≠ 这一类已经覆盖。

> ⚠️ 两个验收脚本都是**按 `LastWriteTime` 取 `release\` 里最新的那个包**，不认版本号。
> 这是为了让版本自增不让它们变红，代价是：**`package.ps1` 失败时它们会静默拿上一个版本的包
> 去认证**，报出来是一片"包名/VersionInfo/接口版本对不上"的假红。第四轮真的踩到过一次
> （打包 OOM 失败、`release\` 里最近的是 0.1.2，于是两个脚本对着一份 0.1.2 的包跑了 10 条 `[FAIL]`；
> 重新打出真的 0.1.4 包之后**一条不留地全绿，产品侧一个字节都没改**）。
> 所以：**看到这一类失败先去看 `release\` 里那个包是不是本次打的**，而不是去查产品。

### 安装时的口令到底写进了什么

向导里问的那一对账号口令，装完之后会出现在**两个地方**：

| 落点 | 谁在用 | 装完之后在哪改 |
|---|---|---|
| `{app}\config.json` 的 `web.user` / `web.password` | 网页控制台的登录框 | 控制台 → 系统设置 → 登录用户名/口令（**存完当场生效**，不用重启） |
| 同一份文件的 `onvif.user` / `onvif.password` | NVR 添加通道时填的 | 控制台 → ONVIF 设置（同样当场生效） |

**同一个值、两个独立字段。** 在控制台改网页那份**不会**动到 NVR 那份，反之亦然
—— 这一点是有意的，但也意味着"我改了密码怎么 NVR 连不上了"要看清楚改的是哪一个。

> ⚠️ **这一条真出过事，而且是三条互不相干的断链，任何一条坏了症状都一样**
> （用户报的正是它：「我用安装包安装的时候设置的 admin 账号密码，没有写入到
> 配置里面，导致初次进入还是 admin 的密码」）：
>
> 1. `.iss` 的 `WriteConfig` 里**只写了 `onvif` 那一组** —— `web` 对象没有
>    `user`/`password` 两个键，于是它落回程序内置的 `admin`/`admin`；
> 2. `start.ps1` **无条件**追加以 `--onvif-user admin --onvif-password admin`，
>    等于每次开服务都把安装时填的那一对踩掉（NVR 那一侧）；
> 3. `start-local.bat` 漏了 `-Portable`，于是它去读
>    `%APPDATA%\Desk2ONVIF\config.json`，而安装包写的是 `{app}\config.json`
>    —— 文件存在、权限正确、内容也对，**读的是另一份**。
>
> 三条的症状都是"我明明设了口令，网页/NVR 却只认 admin"，而日志、安装日志、
> 程序输出里**一个字都不提**。所以现在 `tests\installer_creds.ps1` 拿真安装包
> 走一遍真流程（装 → 读 `{app}\config.json` → 用 `start.ps1 -Portable` 起服务
> → 填的账号能登进去、`admin/admin` 登不进去），并且**三条断链各改坏一处做
> 变异检验**，确认它们各自变红 —— 只验"最后登进去了"是不够的：症状消失只说明
> **至少有一条**修好了，下一次"改了没生效"会从另外两条里长出来。
>
> **这个修复不在旧版本里。** 0.1.6 及更早的安装包装出来仍然是那份坏的
> `web` 配置（`admin`/`admin` 才是能进去的那一对）—— 要拿到它得装 0.1.7 起的包。

> 静默安装（`/VERYSILENT`）的参数、口令为什么必须走环境变量、以及静默路径上和
> 交互式不一样的三处行为，写在 `packaging\README-release.md` 里 —— 那份文件就是
> 装出来的 `README.md`。

## 运行期依赖

`build\bin\` 里除了 `desk2onvif.exe` 还会有 16 个 DLL（FFmpeg 8 个、
OpenSSL 2 个、libuvcpp 及它的依赖 6 个），由构建时自动部署。分发时整个
`bin\` 目录一起拷走即可。

`third_party/` 由脚本生成，不进版本库；依赖的各项说明见
[`third_party/README.md`](../third_party/README.md)。

MSVC 不支持 —— `third_party` 下的依赖全是 MinGW 格式的（`.dll.a`、`.a`），
CMake 配置阶段就会拦下来并说明原因。

## 为什么是 MinGW64 而不是 MSVC

原方案定的是 MSVC。改成 MinGW64 是因为 **libuvcpp 的 SOAP 模块在所有预编译
包里都是关着的**（`UVCPP_WSDL_ENABLE 0`：头文件在，`uvcpp_soap_*` 的符号不在），
而 ONVIF 的 SOAP 信封层要靠它，只能从源码编。从源码编就需要一套和 FFmpeg 的
导入库格式对得上的工具链，MinGW64 是顺理成章的选择。

## 目录

```
├── CMakeLists.txt
├── cmake/                  依赖查找模块
├── scripts/                幂等的依赖供给脚本
├── src/
│   ├── common/             日志、有界队列、配置、防火墙、字符串/HRESULT
│   ├── capture/            DXGI 桌面复制（枚举输出、捕获会话、帧缓冲池、指针合成）
│   ├── encoder/            x264 编码、MP4 封装、MJPEG 快照、fMP4 分片
│   ├── app/                把上面几条线接起来的采集会话（扇出到各下游）
│   ├── rtsp/               Live555 推流：NALU 切分、有界队列、跨线程唤醒
│   ├── onvif/              SOAP 分发、Digest、WS-Discovery、本机地址选择
│   └── web/                HTTP / WebSocket / REST / 静态资源
├── third_party/            依赖产物（生成，gitignore）
├── web/                    Vue 3 配置界面
└── tests/                  冒烟与协议测试（自写探针，不用第三方 ONVIF 库）
```

源码编成 `desk2onvif_core` 静态库，`desk2onvif.exe` 只是薄薄一层命令行 ——
后期的 `tests/` 直接链库做冒烟测试，不用把命令行解析也链进去。
